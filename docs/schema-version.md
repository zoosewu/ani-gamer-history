# 資料格式版本（schemaVersion）

這份文件記錄「不同版本的腳本如何共用同一份紀錄」的決策，以及**什麼時候必須調高 `SNAPSHOT_SCHEMA_VERSION`**。
修改 `src/history/` 的資料格式、合併規則，或新增網站來源之前，請先讀完「調版號規則」。

## 結論

- **只用兩個機制**處理跨版本相容：
  1. **版本檢查**：資料的版本號比腳本支援的高，就拒絕合併，並提示使用者更新腳本；版本號比較低，就先升級轉換再合併。
  2. **相容性自動化測試**：從每個已發佈版本的 git tag 取出真實程式碼，和目前的程式碼互相讀寫，確認不會遺失資料，也不會漏調版號。
- **資料格式一有變動就調版號**，不讓不同格式的版本混用。調版號的代價只是「沒更新的電腦暫時無法同步」；不調的代價是資料被破壞，而且會擴散到每一台電腦。
- **拿不準要不要調時，就調。**

## 背景：0.7.1 的 anime1 重複紀錄

使用者回報同一筆 anime1 紀錄變成兩筆：兩筆的時間戳記精確到毫秒都相同，其中一筆沒有 `seriesId`，來源也變成動畫瘋。

- **根因**：`source` 與 `seriesId` 是 0.6.0 才新增的欄位。0.5.0 以前的版本合併時會丟掉不認得的欄位，再把結果寫回雲端或本機。新版讀到這份「沒有來源」的副本時，把它當成動畫瘋的紀錄，於是變成兩筆。
- **為什麼會有舊版在跑**：另一台電腦、另一個瀏覽器，或更新前就開著的分頁（舊程式碼仍在記憶體裡，直接讀寫 GM storage）。Tampermonkey 預設一天才檢查一次更新。
- **重現方式**：把 0.5.0 tag 的 `src/history/merge.ts` 打包，和新版輪流合併同一份資料，得到的結果和回報的資料完全相同。

## 已查證的各版本行為

以下是從 git tag 讀出的真實程式碼行為。這些版本已經發佈，**行為無法再改變**。

| 版本 | `schemaVersion` | 讀到其他版本號 | 不認得的欄位 | 不認得的 `source` | 分區（bucket） |
|---|---|---|---|---|---|
| 0.4.0、0.5.0 | 1 | `!== 1` 就丟錯，不合併 | 丟掉（含 `source`、`seriesId`） | 整個欄位丟掉 | 全部保留 |
| 0.6.0～0.7.1 | 1 | `!== 1` 就丟錯，不合併 | 丟掉 | 改成 `ani-gamer` | 全部保留 |

其他事實：

- **0.4.0～0.7.1 的 `syncEngine.syncWith` 完全相同**：先 `load()`，丟錯就不會 `save()`。所以雲端檔案的版本號提高後，這些版本會停止同步，不會覆寫雲端。
- **舊版的錯誤訊息是「不支援的資料版本：N」**：這段文字改不動，只能在 readme 說明看到時要更新腳本。
- **舊版讀寫本機儲存時完全不檢查版本號**：GM storage 的 `animeHistory` 欄位直接存 `AnimeHistory`，沒有包裝。
- **版本 1 的資料變形是有限的**：只可能由 0.4.0～0.7.1 寫出，來源只有 `ani-gamer`（使用者 id 分區）和 `anime1`（`@shared` 分區）。

## 沒有採用的方案

### 1. 個案修補（0.7.2 原本的修正）

「`@shared` 裡沒有來源的紀錄視為 anime1」可以修好這次的資料，但不是一勞永逸：

1. **規則寫死在 anime1 上**：之後新增第二個不需登入的網站，它被剝掉來源的副本會被誤判成 anime1。
2. **0.6.0～0.7.1 會把不認得的來源改成動畫瘋**：這幾版已經發佈，未來網站的紀錄經過它們同步，再加上第 1 點，就會被改錯。
3. **每個版本都只保留自己認得的欄位**：下次新增欄位時，新發佈的版本同樣會把更新的欄位丟掉，問題原樣重演。
4. **連結寫死在程式裡**：不認得的來源，卡片連結會錯。

### 2. 讓不同版本繼續混用（由分區決定來源 + `ext` 擴充區）

設計是：每個不需登入的網站有專屬分區，由分區決定 `source`；新欄位一律放進 `ext`，每個欄位各自記錄更新時間，舊版原樣保留不認得的 `ext` 欄位；每筆紀錄存自己的連結。

**沒有採用的原因**：目標是讓不同版本**繼續一起同步**，需要設計和測試的細節很多，而且合併規則本身改變時仍然需要調版號。這個腳本的使用情境是使用者自己的幾台電腦，Tampermonkey 也會自動更新，「暫時停止同步、提示更新」的代價很低，不值得這個複雜度。

## 採用的策略

### 1. 版本檢查的語意

實作在 `src/history/merge.ts`：雲端檔案與 JSON 匯入經過 `parseHistoryAt(version, value)`（同時檢查結構，有問題就丟錯），本機儲存經過 `loadHistoryAt(version, value)`（內容寬鬆處理，避免一筆壞資料讓整份紀錄讀不到）。兩者的版本檢查與升級轉換完全相同。

- **版本號比目前高**：丟出 `SchemaTooNewError`，不合併、不寫入，並提示「請更新腳本」。
- **版本號比目前低**：依序套用 `src/history/migrations.ts` 的轉換，升級到目前版本後再合併。
- **版本號不是 ≥1 的整數**：視為格式錯誤。
- **沒有 `app` / `schemaVersion` 包裝的舊格式**：視為版本 1。

### 2. 本機儲存依版本分開

舊版分頁不會檢查本機儲存的版本號，所以只擋雲端還不夠。**每個版本號用不同的 GM storage 欄位**（實作在 `src/history/versionedStorage.ts`）：

- 版本 1 → `animeHistory`（沿用舊欄位），版本 N ≥ 2 → `animeHistory.vN`。
- 讀取時，讀出版本 1 到目前版本的每個欄位，各自升級轉換後合併；結果和目前欄位不同時立刻寫回。
- 只寫入、只監聽目前版本的欄位。舊欄位不刪除也不寫入，舊分頁因此永遠碰不到新格式的資料。
- 每次載入都重新合併舊欄位：合併是冪等的，已刪除的紀錄靠 `removeTime` 保持刪除，不會復活；更新前就開著的舊分頁後來寫進舊欄位的紀錄，也會在下次載入時收進來。
- 欄位名稱由版本號產生，**調版號時不需要改 `versionedStorage.ts` 或 `localStore.ts`**。

### 3. 升級轉換的規則

- **一個版本號一段轉換**：`migrations[N]` 把版本 N 的資料轉成版本 N+1。
- **轉換程式必須凍結**：寫好之後不再修改；不能 import 之後可能改變的現行 helper（例如 `sourceOf`、`DEFAULT_SOURCE`），需要的常數直接寫在轉換程式裡。
- **只依賴「該版本號資料的變形是有限的」**：例如版本 1 → 2 的「`@shared` 裡沒有來源或來源是 `ani-gamer` 的紀錄改成 `anime1`」，在版本 1 是正確的，因為版本 1 只有這兩種來源。這條規則**不能**套用到版本 2 以後的資料。
- 轉換後的資料一律再經過目前的 `normalizeHistory`。

### 4. 相容性自動化測試

實作在 `src/history/compat/`，由 `npm test` 執行：`releases.ts` 取出並打包已發佈版本，`fixtures.ts` 是目前格式的完整測試資料，`v1.ts` 是凍結的版本 1 測試資料，`compat.test.ts` 是測試本身。

- **不把舊版程式碼複製進 repo**：測試時用 `git archive` 從每個 tag 取出 `src/`，再用 esbuild 打包該 tag 的 `src/history/merge.ts`（`@/` 指向該 tag 自己的 `src`）。每次發佈都會自動納入，沒有「忘記凍結」這個步驟。
- **需要完整的 git 歷史與 tag**：淺層 clone 或找不到 tag 時，測試直接失敗，不會略過。本機請先執行 `git fetch --tags`；CI 的 checkout 設定 `fetch-depth: 0`。
- **對每個已發佈版本 T（版本號 sT）與目前版本號 S**：
  - **sT > S**：失敗。代表有 tag 的版本號比目前程式碼還新。
  - **sT < S**：
    - T 必須拒絕讀取目前版本寫出的資料。
    - 凍結的版本 sT 測試資料經過 T 讀寫一次（產生該版本真實的變形，例如 0.5.0 會剝掉欄位）後，目前版本必須能升級成預期的結果，而且和原始資料合併後沒有重複或遺失。
  - **sT = S**：
    - 目前版本寫出的資料，經過 T 讀取再寫出後，目前版本讀回來必須**完全相同**。
    - 本機儲存的路徑（`normalizeHistory`）同樣必須無損。
    - 目前版本和 T 輪流合併、更新進度多輪，不能有重複或遺失。
- **測試資料會強迫跟著型別更新**：`fixtures.ts` 用 `{ [S in AnimeSource]: Required<Anime> }` 為每個來源寫一筆所有欄位都填滿的紀錄。新增欄位或來源時沒有補上，`tsc`（`npm run build`）就會失敗。補上之後，如果同版本號的已發佈版本會丟掉或改掉它，上面的「sT = S」測試就會失敗，提醒你必須調版號。
- **公開 API 是測試的前提**：每個 tag 的 `src/history/merge.ts` 必須匯出 `parseSnapshot`、`createSnapshot`、`mergeHistory`、`normalizeHistory`，`src/history/types.ts` 必須匯出 `SNAPSHOT_SCHEMA_VERSION`。之後如果搬移或改名，要在 `src/history/compat/releases.ts` 加上依版本的對應。

### 5. 被擋下時的提示

- **同步**：同步狀態記錄 `updateRequired`，同步狀態顯示「無法同步」；設定 dialog 的同步狀態頁與首頁的同步指示都會出現「請更新腳本」連結（`src/scriptMeta.ts` 的 `SCRIPT_DOWNLOAD_URL`，與 userscript 的 `updateURL` 共用），Tampermonkey 選單的同步通知也會帶出訊息。
- **JSON 匯入**：顯示同一個訊息。
- **舊版（0.4.0～0.7.1）**：只會顯示「不支援的資料版本：N」，readme 的「雲端同步」段有說明。

## 調版號規則

**判斷方式**：假設同版本號、最舊的已發佈版本讀進新資料後再寫回去。只要有任何資訊會**遺失或被解讀成不同意思**，就必須調版號。

**一定要調**：

- 新增、刪除或改名 `Anime` 的欄位
- 新增網站來源（新的 `AnimeSource`）
- 改變分區的意義（例如新增一種不綁使用者的分區、改變哪些紀錄放在哪個分區）
- 改變合併規則（去重的鍵、哪一邊的值優先、刪除與最愛的判斷）
- 改變欄位的意義、單位或預設值
- 改變 `normalizeAnime` 會丟掉或改寫的內容

**不用調**：

- 只改 UI、標記樣式、文字
- 只改同步時機、adapter 的傳輸方式（例如新的雲端平台）
- 不影響讀寫結果的重構
- 本機偏好設定、同步設定（存在其他 GM 欄位，不屬於紀錄資料）

**拿不準時就調。** 自動化測試只能抓到「欄位遺失」這類結構上的問題；「同樣的資料被解讀成不同意思」（例如分區語意改變）要靠這份規則判斷。

## 調版號的步驟

1. `src/history/types.ts`：`SNAPSHOT_SCHEMA_VERSION` 加 1。
2. `src/history/migrations.ts`：加上「舊版本號 → 新版本號」的轉換，遵守上面的「升級轉換的規則」。
3. `src/history/compat/`：為舊版本號加一份凍結的測試資料與升級後的預期結果（參考 `v1.ts`；`upgraded` 是**下一個**版本號的資料），並加進 `compat.test.ts` 的 `frozenFixtures`。
4. 更新這份文件的「已查證的各版本行為」與「版本紀錄」。
5. commit 內文說明「未更新的電腦會暫時無法同步」。不要用 `feat!` 或 `BREAKING CHANGE`：release-please 在 1.0.0 以前遇到它們會直接升到 1.0.0。

本機儲存欄位由版本號自動產生，不用修改。

## 代價

- **資料格式一有變動就要調版號**：新增欄位、新增來源幾乎每次都算。
- **調版號後，沒更新的電腦會暫時無法同步**：Tampermonkey 預設一天內會自動更新，也可以手動檢查更新。本機的紀錄照常可用，更新後會自動升級並合併，不會遺失。
- **升級轉換會越來越多**：每段轉換都凍結且有自動化測試保護，不需要回頭維護。
