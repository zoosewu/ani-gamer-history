# 資料版本（dataVersion）

這份文件記錄「不同版本的腳本如何共用同一份紀錄」的決策，以及**什麼時候、要怎麼調資料版本 `DATA_VERSION`**。
修改 `src/history/` 的資料格式、合併規則，或新增網站來源之前，請先讀完「調資料版本的規則」。

## 結論

- **資料版本獨立於腳本版本**，用語意化版號 `MAJOR.MINOR.PATCH` 記錄在 `src/history/types.ts` 的 `DATA_VERSION`。看版號就知道資料格式什麼時候改過、改了哪一種。
- **雲端、匯出的 JSON、本機都只存一份最新版的資料**，而且資料本身帶著 `dataVersion`。
- **只用兩個機制**處理跨版本相容：
  1. **版本檢查**：資料的 `MAJOR.MINOR` 比腳本新，就拒絕使用，並提示使用者更新腳本；比腳本舊，就先升級再使用。
  2. **相容性自動化測試**：從每個已發佈版本的 git tag 取出真實程式碼，和目前的程式碼互相讀寫，確認不會遺失資料，也不會漏調版號。
- **資料格式一有變動就調版號**，不讓不同格式的腳本混用。調版號的代價只是「沒更新的電腦暫時不能用」；不調的代價是資料被破壞，而且會擴散到每一台電腦。
- **拿不準要調哪一層時，就調高一層。**

## 背景：0.7.1 的 anime1 重複紀錄

使用者回報同一筆 anime1 紀錄變成兩筆：兩筆的時間戳記精確到毫秒都相同，其中一筆沒有 `seriesId`，來源也變成動畫瘋。

- **根因**：`source` 與 `seriesId` 是 0.6.0 才新增的欄位。0.5.0 以前的版本合併時會丟掉不認得的欄位，再把結果寫回雲端或本機。新版讀到這份「沒有來源」的副本時，把它當成動畫瘋的紀錄，於是變成兩筆。
- **為什麼會有舊版在跑**：另一台電腦、另一個瀏覽器，或更新前就開著的分頁（舊程式碼仍在記憶體裡，直接讀寫 GM storage）。Tampermonkey 預設一天才檢查一次更新。
- **重現方式**：把 0.5.0 tag 的 `src/history/merge.ts` 打包，和新版輪流合併同一份資料，得到的結果和回報的資料完全相同。

## 已查證的各版本行為

以下是從 git tag 讀出的真實程式碼行為。這些版本已經發佈，**行為無法再改變**。

| 版本 | 資料版本 | 讀到其他版本號 | 不認得的欄位 | 不認得的 `source` | 分區（bucket） |
|---|---|---|---|---|---|
| 0.4.0、0.5.0 | 1（`schemaVersion: 1`） | `!== 1` 就丟錯，不合併 | 丟掉（含 `source`、`seriesId`） | 整個欄位丟掉 | 全部保留 |
| 0.6.0～0.7.1 | 1（`schemaVersion: 1`） | `!== 1` 就丟錯，不合併 | 丟掉 | 改成 `ani-gamer` | 全部保留 |

其他事實：

- **0.4.0～0.7.1 的 `syncEngine.syncWith` 完全相同**：先 `load()`，丟錯就不會 `save()`。所以雲端檔案的版本號提高後，這些版本會停止同步，不會覆寫雲端。
- **舊版的錯誤訊息是「不支援的資料版本：N」**：這段文字改不動，只能在 readme 說明看到時要更新腳本。
- **舊版讀寫本機儲存時完全不檢查版本號**：GM storage 的 `animeHistory` 欄位直接存 `AnimeHistory`，沒有包裝。
- **0.8.0**：雲端只看整數 `schemaVersion`（大於 2 就拒絕並提示「請先更新腳本」）；本機直接讀寫 `animeHistory.v2`，同樣沒有包裝、不檢查版本。
- **版本 1 的資料變形是有限的**：只可能由 0.4.0～0.7.1 寫出，來源只有 `ani-gamer`（使用者 id 分區）和 `anime1`（`@shared` 分區）。

## 沒有採用的方案

### 1. 個案修補（0.7.2 原本的修正）

「`@shared` 裡沒有來源的紀錄視為 anime1」可以修好這次的資料，但不是一勞永逸：

1. **規則寫死在 anime1 上**：之後新增第二個不需登入的網站，它被剝掉來源的副本會被誤判成 anime1。
2. **0.6.0～0.7.1 會把不認得的來源改成動畫瘋**：這幾版已經發佈，未來網站的紀錄經過它們同步，再加上第 1 點，就會被改錯。
3. **每個版本都只保留自己認得的欄位**：下次新增欄位時，新發佈的版本同樣會把更新的欄位丟掉，問題原樣重演。
4. **連結寫死在程式裡**：不認得的來源，卡片連結會錯。

### 2. 讓不同版本繼續混用（由分區決定來源 + `ext` 擴充區）

設計是：每個不需登入的網站有專屬分區，由分區決定 `source`；新欄位一律放進 `ext`，每個欄位各自記錄更新時間，舊版原樣保留不認得的 `ext` 欄位；每筆紀錄存自己的連結。

**沒有採用的原因**：目標是讓不同版本**繼續一起同步**，需要設計和測試的細節很多，而且合併規則本身改變時仍然需要調版號。這個腳本的使用情境是使用者自己的幾台電腦，Tampermonkey 也會自動更新，「暫時停止同步、提示更新」的代價很低，不值得這個複雜度。

## 採用的策略

### 1. 資料格式

雲端檔案、匯出的 JSON、本機儲存都是同一個格式（`createSnapshot()` 產生）：

```json
{ "app": "ani-gamer-history", "dataVersion": "2.0.0", "schemaVersion": 2, "exportedAt": 0, "history": {} }
```

- **`dataVersion`**：資料版本，新腳本只看這個欄位。
- **`schemaVersion`**：只給 0.4.0～0.8.0 看的整數閘門，由 `legacySchemaVersion()` 算出：
  - 資料是 `2.0.x` 時寫 `2`，0.8.0 讀得懂，照常同步。
  - MINOR 或 MAJOR 往上調之後一律寫 `3`，0.8.0 會拒絕並提示「請先更新腳本」，0.4.0～0.7.1 本來就只接受 `1`。
  - 之後不會再用它表示其他意義。
- **讀到沒有 `dataVersion` 的資料**（0.8.0 以前寫的）：整數 `schemaVersion` N 視為 `N.0.0`；連包裝都沒有的舊格式視為 `1.0.0`。

### 2. 版本檢查

實作在 `src/history/dataVersion.ts` 與 `src/history/merge.ts`，雲端、JSON 匯入、本機儲存**都經過同一個檢查**：

- **資料的 MAJOR 或 MINOR 比腳本新**：丟出 `SchemaTooNewError`，不合併、不寫入，提示「這份資料由較新版本的腳本建立（資料版本 X.Y.Z），請先更新腳本」。
- **只有 PATCH 比腳本新**：照常使用（PATCH 的定義就是舊腳本讀寫後無損）。
- **比腳本舊**：MAJOR 較舊時依序套用 `src/history/migrations.ts` 的轉換；MINOR、PATCH 較舊不需要轉換。
- **版本號格式不對**：視為格式錯誤。

### 3. 本機儲存：只存一份，版本太新就鎖定

實作在 `src/history/localSnapshot.ts`、`localStore.ts`、`persistence.ts`：

- **只用一個 GM 欄位 `history`**，內容就是上面的格式。之後調資料版本時欄位名稱不變，只改裡面的 `dataVersion`。
- **不沿用 `animeHistory.v2` 的名稱**：0.8.0 會把它當成沒有包裝的紀錄直接合併，寫進包裝過的格式會被更新前開著的 0.8.0 分頁弄壞。
- **舊欄位遷移後刪除**：載入時只要 `animeHistory`（1.0.0）或 `animeHistory.v2`（2.0.0）還在，就升級後併進 `history`，再用 `GM_deleteValue` 刪掉。更新前開著的舊分頁如果又寫出舊欄位，下次載入時會再被收進來並刪除，最後永遠只剩 `history`。
- **本機資料比腳本新時鎖定**（store 的 `storage.lockedBy`）：
  - 不讀取、不合併、不寫入本機資料，也不動舊欄位。
  - 不做雲端同步，也不能匯入、匯出 JSON（匯出的會是空的）。
  - 首頁「本機歷史紀錄」不顯示清單，改顯示提示與「請更新腳本」連結；同步指示與設定 dialog 也會提示。
  - **已經開著的分頁也會鎖定**：收到其他分頁寫入較新版本資料的通知時立刻鎖定，之後看動畫也不會蓋掉新資料。這正是 0.7.1 重複紀錄的成因：開著的舊分頁用舊程式把新資料寫回去。
- **已發佈版本的限制**：0.4.0～0.8.0 不認得 `history`，新版刪掉它們的欄位後，它們只會看到空的本機紀錄，不會碰到新資料；雲端則由 `schemaVersion` 擋住。從 0.9.0 起的腳本都會檢查 `history` 的 `dataVersion`，之後每次調版號都會自動生效。

### 4. 升級轉換的規則

- **一個 MAJOR 一段轉換**：`migrations[N]` 把 MAJOR N 的資料轉成 N+1。MINOR、PATCH 不需要轉換。
- **轉換程式必須凍結**：寫好之後不再修改；不能 import 之後可能改變的現行 helper（例如 `sourceOf`、`DEFAULT_SOURCE`），需要的常數直接寫在轉換程式裡。
- **只依賴「該版本資料的變形是有限的」**：例如 1 → 2 的「`@shared` 裡沒有來源或來源是 `ani-gamer` 的紀錄改成 `anime1`」，在 1.x 是正確的，因為 1.x 只有這兩種來源。這條規則**不能**套用到 2.x 以後的資料。
- 轉換後的資料一律再經過目前的 `normalizeHistory`。

### 5. 相容性自動化測試

實作在 `src/history/compat/`，由 `npm test` 執行：`releases.ts` 取出並打包已發佈版本，`fixtures.ts` 是目前格式的完整測試資料，`v1.ts` 是凍結的 1.0 測試資料，`compat.test.ts` 是測試本身。

- **不把舊版程式碼複製進 repo**：測試時用 `git archive` 從每個 tag 取出 `src/`，再用 esbuild 打包（`@/` 指向該 tag 自己的 `src`）。每次發佈都會自動納入。
- **每個 tag 的資料版本**：有 `DATA_VERSION` 就用它，0.8.0 以前用 `SNAPSHOT_SCHEMA_VERSION` 換算成 `N.0.0`。
- **需要完整的 git 歷史與 tag**：淺層 clone 或找不到 tag 時測試直接失敗，不會略過。本機請先 `git fetch --tags`；CI 的 checkout 設定 `fetch-depth: 0`。
- **依 `MAJOR.MINOR` 比較每個 tag 與目前版本**：
  - **tag 較新**：失敗。
  - **tag 較舊**：tag 必須拒絕目前的資料；該版本的凍結測試資料經過 tag 讀寫一次後（產生真實的變形，例如 0.5.0 會剝掉欄位），目前版本必須升級成預期結果，沒有重複或遺失。
  - **相同**：目前的資料經過 tag 讀寫後必須**完全相同**；本機儲存的路徑也必須無損；輪流合併、更新多輪不能有重複或遺失。
- **測試資料會強迫跟著型別更新**：`fixtures.ts` 用 `{ [S in AnimeSource]: Required<Anime> }` 為每個來源寫一筆所有欄位都填滿的紀錄。新增欄位或來源時沒有補上，`tsc`（`npm run build`）就會失敗；補上之後，如果同一個 `MAJOR.MINOR` 的已發佈版本會丟掉它，「相同」那組測試就會失敗，提醒你必須調 MINOR 以上。
- **公開 API 是測試的前提**：每個 tag 的 `src/history/merge.ts` 必須匯出 `parseSnapshot`、`createSnapshot`、`mergeHistory`、`normalizeHistory`，`src/history/types.ts` 必須匯出 `DATA_VERSION`（0.8.0 以前是 `SNAPSHOT_SCHEMA_VERSION`）。之後如果搬移或改名，要在 `releases.ts` 加上依版本的對應。

## 調資料版本的規則

**判斷方式**：假設最舊的、同一個 `MAJOR.MINOR` 的已發佈腳本讀進新資料後再寫回去。只要有任何資訊會**遺失或被解讀成不同意思**，就不能只調 PATCH。

| 層級 | 什麼時候調 | 舊腳本讀到時 | 新腳本讀到舊資料時 |
|---|---|---|---|
| **MAJOR** | 既有資料要轉換才能用：欄位改名、改義、改單位或預設值；改變分區的意義；改變合併規則（去重的鍵、哪一邊優先、刪除與最愛的判斷） | 拒絕 | 依 `migrations[MAJOR]` 轉換 |
| **MINOR** | 只有新增，舊資料原樣可用：新增欄位、新增網站來源（新的 `AnimeSource`） | 拒絕（否則會丟掉新欄位） | 直接使用 |
| **PATCH** | 同一個 `MAJOR.MINOR` 的舊腳本讀寫後完全無損、解讀也相同的修正 | 接受 | 直接使用 |

**不用調**：

- 只改 UI、標記樣式、文字
- 只改同步時機、adapter 的傳輸方式（例如新的雲端平台）
- 不影響讀寫結果的重構
- 本機偏好設定、同步設定（存在其他 GM 欄位，不屬於紀錄資料）
- 只改變資料的存放位置（例如這次本機改成單一欄位）

**拿不準時就調高一層。** 自動化測試只能抓到「欄位遺失」這類結構上的問題；「同樣的資料被解讀成不同意思」（例如分區語意改變）要靠這份規則判斷。

## 調資料版本的步驟

1. `src/history/types.ts`：調 `DATA_VERSION`。調 MINOR 或 MAJOR 時，`schemaVersion` 會自動變成 `3`，擋住 0.8.0。
2. 調 MAJOR 時：在 `src/history/migrations.ts` 加上「舊 MAJOR → 新 MAJOR」的轉換，遵守「升級轉換的規則」。
3. 調 MINOR 或 MAJOR 時：在 `src/history/compat/` 為**舊的** `MAJOR.MINOR` 加一份凍結的測試資料（參考 `v1.ts`：`version` 是舊版本，`upgradedVersion` / `upgraded` 是升級到新版本後應有的內容），並加進 `compat.test.ts` 的 `frozenFixtures`。
4. 更新這份文件的「已查證的各版本行為」與「版本紀錄」。
5. commit 內文說明「未更新的電腦會暫時無法使用」。不要用 `feat!` 或 `BREAKING CHANGE`：release-please 在 1.0.0 以前遇到它們會直接升到 1.0.0。

本機儲存的欄位名稱不變，不用修改。

## 代價

- **資料格式一有變動就要調版號**：新增欄位、新增來源至少是 MINOR。
- **調 MINOR 以上之後，沒更新的電腦會暫時無法使用**：Tampermonkey 預設一天內會自動更新，也可以手動檢查更新。更新後資料會自動升級，不會遺失。
- **升級轉換會越來越多**：每段轉換都凍結且有自動化測試保護，不需要回頭維護。
